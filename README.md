# ブラウン管TV 配信プラットフォーム

ブラウン管TV画面の外観を維持し、チャット → ローカルLLM → Speech.cpp → SoulX-FlashHead Lite → TV画面の音声・動画再生を連携します。

## 起動

PowerShellでこのフォルダーを開いて実行します。

```powershell
$env:PYTHONUTF8='1'
uv run --link-mode=copy server.py
```

または `./start.ps1` を実行します。実行ポリシーの変更は不要です。スクリプトが制限される場合は上記のuvコマンドを使ってください。

- チャット: <http://127.0.0.1:17863/>
- TV: <http://127.0.0.1:17863/ブラウン管TV_配信プラットフォーム.html>
- 旧HTML名のURLも新URLへ転送されるため、既存のブックマーク・OBS設定から利用できます。
- 無音プレビュー: TVのURL末尾に `?preview=1` を追加します。
- 稼働状態: <http://127.0.0.1:17863/health>

ボタン操作なしで自動再生する場合は、サーバー起動後、別のPowerShellで `./open-tv.ps1` を実行してください。自動再生を許可した配信用Chromeが開きます。合成完了後は待機動画の終端に合わせて音声を自動再生します。通常のChromeとは別のプロファイルを使います。このウィンドウでは配信用のローカル画面を使用してください。

通常ブラウザでもOBSでも同じTV URLを使います。HTMLをダブルクリックする方法では、チャット・LLM連携は動きません。URLを通常のChromeで直接開くと、ブラウザの初回自動再生制限が適用される場合があります。HTML側だけでは解除できないため、ボタンを押さずに使う場合は `open-tv.ps1` を利用してください。OBSのブラウザソースでは専用Chromeは不要です。

TVが非表示になると、安全のため進行中の発話をキャンセルします。ブラウザ利用時は、チャットとTVを別ウィンドウにしてTVを表示しておいてください。最初に開いた通常TVだけが音声再生権を持ちます。`open-tv.ps1` で開いた画面は、音声を出せることを確認してから待機中の再生権を自動取得します。発話準備・再生・終了待ちの間は変更を拒否します。明示的なプレビュー（`?preview=1`）は再生先になりません。OBSへ変更する際は先のTVを閉じ、OBSソースを読み込み直してください。既存の「再生」ボタンは動画の再生用で、音声の有効化・再生先の変更には使いません。

## LLMとSpeech.cpp

`config.toml` の接続先・声質・タイミングを編集し、サーバーを再起動すると反映されます。`.env` は使用しません。

- 確認済みLLM: `http://127.0.0.1:1067/v1`、`Qwen3.5-35B-A3B-GGUF-UD-MXFP4_MOE`。llama.cppの`chat_template_kwargs.enable_thinking`へチャットの思考設定を変換します。
- Speech.cpp: 0.10.1、`irodori-tts-mf`。初回発話時に管理プロセスを起動し、その後はモデルを常駐させます。
- 実行ファイルの探索順: `speech.executable` 設定、PATH上の `speech`、`%LOCALAPPDATA%/Programs/speech.cpp/0.10.1/speech.exe`。
- 未導入の場合は[公式のWindows導入手順](https://github.com/nyosegawa/speech.cpp#install)で導入するか、`[speech]` に `executable = 'C:\path\to\speech.exe'` を追加します。
- モデル名による初回取得には約1.92GBのダウンロードが必要です。先に `speech pull irodori-tts-mf` で取得できます。取得中はサーバーからの発話試験を避けてください。
- 実行優先順はGPU → CPU。GPU初期化・合成に失敗すると、管理中のSpeech.cppだけを終了してCPUで再試行します。LLM・OBSは停止しません。
- 声質は `甲高い女性の声で、ツンデレっぽい喋り方です。`、seed 42です。`speech.reference_audio` の基準音声を起動時に `reference` として登録し、各文の合成で共通して使用します。GPUからCPUへ切り替わった場合も同じ音声を登録します。基準音声が欠損・不正な場合は読み上げを失敗扱いにし、別の声へ自動変更しません。
- 基準音声は `基準音声/` に置き、`config.toml` の `reference_audio` にファイルへの相対パスまたは絶対パスを指定します。このフォルダーはGit管理対象外です。別の環境では同じ位置へ音声を用意するか、設定を変更してください。意図的に参照音声なしへ戻す場合だけ `reference_audio = ""` にします。
- 長い返答は句読点と最大70文字で分割し、順に合成してWAVへ結合します。思考過程・中断・空応答・長さ制限で途切れた返答は読み上げません。

Speech.cppのログは `.runtime/speech.log` に保存します。サーバーの終了時は、管理中のSpeech.cppも終了します。

## SoulXリップシンク

生成動画だけを確認する画面は `http://127.0.0.1:17863/web/soulx-review.html` です。CRT効果や位置補正を通さず、映像・音声をそのまま再生できます。保存済みテスト動画の選択、スロー再生、25fps基準のコマ送り、手元のMP4の読み込みに対応します。TVの再生権は取得せず、自動再生もしません。以後の生成成功時には最新1本を`.runtime/review/latest.mp4`へ保存し、通常の発話終了・クリア後も確認用に保持します。次の生成成功時に上書きします。

`./install-soulx.ps1`でaudio.cpp v0.9.4、CUDA 12.4ランタイム、SoulX-FlashHead Lite Q8モデルを導入します。公式ファイルのSHA-256を検証します。実行ポリシーは変更しません。参照画像は`soulx_flashhead_windows_rtx4090_quickstart/avatar.jpg`です。依存ソース、ランタイム、モデル、生成結果はGit管理対象外です。

合成したWAV全体を入力し、512×512・4ステップ・seed 42で動画を生成します。推論用のみ16kHzモノラルへ変換し、MP4へは元の合成音声を結合します。H.264/AACと長さの検証後に公開し、TVで映像と音声を同じ再生時計で再生します。この経路では音声の150ms先行は使いません。待機終端の300ms前に発話フラグON、動画終端の200ms前にOFF、実際の動画終端で待機へ戻ります。

チャットには動画準備・SoulX生成・音声結合の段階と経過秒を表示します。未完了の動画は再生しません。`[video]`の`timeout_seconds=600`、`max_audio_seconds=180`、`disk_reserve_gib=10`を超える場合、GPUエラー、再生前の動画読み込み失敗では固定D＋元の音声へ切り替え、チャットに理由を残します。再生開始後の障害は停止し、自動で最初から読み直しません。動画生成にCPU再試行は行いません。

生成は1件ずつです。終了・クリアで発話データを回収し、生成中のクリアでは子プロセスも終了します。生成失敗の詳細は`.runtime/video/last-error.log`、実測結果は`.runtime/soulx-verification.json`です。`video.enabled=false`で固定D方式へ戻せます。LLMやOBSのメモリ設定は自動変更しません。

実モデル試験は、先に`.runtime/lipsync-sample.wav`へ確認用合成音声を用意し、`uv run --link-mode=copy python tests/verify_soulx.py`を実行します。3秒・5秒・10秒の動画生成、長さとストリームの検証、総VRAMピークと処理時間を記録します。

## 動画と音声の動作（固定Dへの切り替え時）

チャットには発話ごとの状態を表示します。「順番待ち → モデル・基準音声読み込み → 合成中（完了数／総数・経過秒・デバイス） → 再生待ち → 再生中 → 完了」と進み、失敗した場合は理由を表示します。GPU失敗後のCPU再試行、TV未接続・再生準備待ち、通信断も区別します。チャットの再接続時は現在の状態を取得し直します。状態表示は会話本文やLLMの入力履歴には含めません。

起動時はA。待機中はA・B・Cを各動画の終端で切り替え、直前と同じ素材は続けません。Dから待機へ戻る際は3本すべてが候補です。待機用のXYZ設定は3本共通、Dは既存の独立した設定です。

LLM生成・TTS生成中は待機を続けます。音声のデコードとDの準備ができた後、待機動画の終端に合わせてフラグONと音声開始を予約します。

| 設定 | 初期値 | 動作 |
|---|---:|---|
| `flag_lead` | 0.300秒 | 待機終端の手前でフラグON |
| `audio_lead` | 0.150秒 | 待機終端の手前で音声開始。短音声は音声長の25%まで縮小 |
| `off_lead` | 0.200秒 | 音声終了の手前でOFF。次のD終端が早ければ延期 |
| `max_idle_overlap` | 0.300秒 | 音声開始後、Dへ移行できなければ音声を停止 |
| `queue_limit` | 10件 | 合成中・再生待ち・再生中・D終了待ちの合計上限 |

Dから待機へ戻るには、実際の音声終了とDの終端の両方が必要です。音声中はフラグOFFでもDを維持します。次の発話は、待機動画を1本挟んでから始めます。

「停止」は進行中のLLM生成を中断します。「クリア」はLLM・合成・発話キュー・進行中音声を取り消します。TVの停止、比較モード、リセット、フラグ手動操作、素材変更、設定読込も、先に自動発話をキャンセルしてから適用します。手動で画像・動画を選んだ場合は自動発話・ランダム待機を休止します。標準動作へ戻すにはTVを読み込み直してください。

通信断、非表示化、音声コンテキスト停止、映像切り替え失敗では音声を停止します。途中まで再生した発話は再試行しません。ブラウザやOSが停止している間の厳密なミリ秒保証はできませんが、復帰時には予定時刻だけで再生を続けず、安全側に停止します。

## OBS設定

1. 通常ブラウザで音声を持つTVを開いている場合は閉じます。確認用には `?preview=1` を使います。
2. OBSでブラウザソースを追加し、ローカルファイルの指定を解除してTV URLを指定します。
3. 検証時のブラウザソースサイズは1600×1000です。画面のUI・調整パネルも元HTMLのまま含まれます。必要ならOBS側でクロップしてください。
4. 「OBSを介して音声を制御する」を有効にし、ミキサーにブラウザソースが表示されることを確認します。
5. 「表示されていないときにソースをシャットダウンする」「シーンがアクティブになったときにブラウザの表示を更新する」はOFFを推奨します。再読み込み・非表示による中断を避けるためです。
6. TVは素材動画をミュートし、合成音声だけを出力します。デスクトップ音声と音声モニタリングを併用する場合は、OBS側で同じ音が二重に取り込まれないようにしてください。

ブラウザソースの操作が必要な場合はOBSの「対話」を開き、既存の再生ボタンを押してください。音声が止まる場合はチャットのエラー表示、`.runtime/speech.log`、`.runtime/video/last-error.log`を確認してください。

## テストと設計判断

```powershell
uv run --link-mode=copy pytest -q
npm ci
npm test
# サーバーを起動した状態で実行。既定ではインストール済みChromeを使用します。
npm run test:browser
```

Chromeが別の場所にある場合は `$env:CHROME_PATH='C:\path\chrome.exe'` を設定します。ブラウザテストは実動画とテスト用WAV・WebSocketを使い、LLM/TTSを繰り返し呼ばずに異常系を再現します。結果は `.runtime/browser-results.json` に出力します。

サーバーが会話世代・発話ID・単一キュー・単一再生権を管理し、映像と音声のタイミング判断はTV内だけで行います。遅れた通知・古い完了イベントで次の発話を終了させないための分担です。静的配信は公開対象のHTML・JS・動画・画像だけに制限し、サーバーコードや設定ファイルを公開しません。ループバック限定・同一オリジン限定で運用します。

確認結果の詳細は `VERIFICATION.md` を参照してください。
